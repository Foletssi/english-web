## 4. 参考的主流实现

并非“搜索完所有网站”，这里核对了适合本项目的官方源码和文档：

1. [WordPress wp_trash_post 源码](https://developer.wordpress.org/reference/functions/wp_trash_post/)：
   保存原状态和删除时间，再切换到 trash，成功更新后才触发完成事件。
2. [WordPress wp_untrash_post 源码](https://developer.wordpress.org/reference/functions/wp_untrash_post/)：
   普通内容默认恢复为 draft，而非直接重新公开。该行为比恢复后立即上线更适合需要人工核对字幕的教学视频。
3. [Cloudflare R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)：
   bucket.delete 删除的是对象文件，不会替你删除 Supabase 记录、HLS 引用或处理任务；单次最多 1,000 个 key，需要分批。
4. [PostgreSQL 显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)：
   云端版本已使用行锁、内容 revision 和单个数据库事务处理多人同时修改快照。

WordPress 源码里核心区别是：

~~~php
// wp_trash_post: 保存原状态和删除时间
add_post_meta($post_id, '_wp_trash_meta_status', $previous_status);
add_post_meta($post_id, '_wp_trash_meta_time', time());
// wp_untrash_post: 普通文章默认回到草稿
$new_status = ('attachment' === $post->post_type) ? 'inherit' : 'draft';
~~~

我们借鉴的是「状态变更 + 关联数据保留 + 恢复审核」，没有把 WordPress 或其他 CMS 安装到你的项目里。

### 5.1 单条、批量删除的真实调用顺序

~~~text
按钮点击
  → 检查管理端会话 + 本地模式 + 选择数量
  → 确认提示（条数/标题/影响范围）
  → Store.deleteVideos(ids)
      → 读取最新快照，不使用弹窗打开时的旧对象
      → 按 ID 去重
      → 整批检查 PROCESSING / QUEUED / UPLOADING 视频及任务
      → 有任一运行中任务则整批拒绝，不先删除前几条
      → 每条 video + sentences + jobs 放进 trash
      → 写入 tombstones
      → 从有效 videos / sentences / jobs 移除
      → 一次 localStorage.setItem 序列化整个快照
      → 成功后才派发 content-changed
  → 管理端刷新表格、数量，并提示成功
  → 同 Origin 学员页收到 storage 后更新视图、停止被删视频
~~~

一次 setItem 对本次完整快照是原子替换，但 **localStorage 不等于跨标签页数据库事务**。两个管理员标签页同时写入存在最后写入者覆盖的风险；本地验收建议只开一个可编辑管理端。多人正式管理应进入第 7 节的服务端事务方案，而不是继续扩展前端锁。

### 5.2 恢复逻辑

~~~text
找回收站条目 → 检查有效列表无同 ID 冲突
→ 视频恢复为 DRAFT，publishedAt 清空
→ 字幕和任务快照回填
→ 从 trash 移除
→ tombstone.deleted = false，但 ignoredJobIds 保留
→ 一次持久化 → 提示重新审核发布
~~~

恢复不会重新消耗 AI；有错误任务时，可以由管理员主动点击「重试」。重新导入的视频使用新 ID，避免旧媒体版本互相覆盖。

### 5.3 为什么后台不再复活删除视频

权威实现：[admin/assets/studio-v2.js](E:/英语网页制作/Eastudy_Composite_V1_Beta6_17_VocabularyLogic/admin/assets/studio-v2.js)。

~~~js
// ensureVideo 的第一道检查；后续 mergeResult / syncJobs / pollJob 同样检查。
if (!Store.acceptsJob(videoId, job.id)) return null;

// acceptsJob 使用三项条件，而不是只看“视频是否存在”

  && !(tombstone?.ignoredJobIds || []).includes(jobId)
  && (!existingVideo || existingVideo.localStudioJobId === jobId);
~~~

## 7. 云端可恢复删除实现与后续永久删除方案

现有数据库是 **private.content_snapshots**，其中 draft / published 是 JSONB。
不能直接写一份针对 public.videos 的 DELETE SQL，然后声称已经打通。

### 7.1 线上接口

~~~ts
POST /api/admin/videos/trash
body: { videoIds: string[], expectedRevision: number, requestId: string }

POST /api/admin/videos/restore
body: { videoId: string, expectedRevision: number, requestId: string }

GET /api/admin/videos/trash

POST /api/admin/videos/purge
body: { videoId: string, expectedRevision: number, requestId: string }
~~~

服务端依次校验 JWT、public.is_admin()、ID 数量、expectedRevision。403 表示无权限，409 表示版本冲突或任务仍运行，404 表示目标不存在；客户端遇到 409 先刷新，不覆盖别人的编辑。重复 requestId 返回之前的结果。

### 7.2 快照删除的 SQL 核心示例

以下逻辑已写入 [20260908_content_video_trash.sql](E:/英语网页制作/Eastudy_Composite_V1_Beta6_17_VocabularyLogic/supabase/migrations/20260908_content_video_trash.sql)。部署时在真实 Supabase 执行并验证；草稿保存也会增加 revision，使删除前的冲突检查能覆盖刚发生的编辑。

~~~sql
-- 纯函数：只移除指定内容，不把未审核草稿重新发布。
create or replace function private.without_video(s jsonb, vid text)
returns jsonb language sql immutable set search_path = ''
as $$
  select s || jsonb_build_object(
    'videos', coalesce((
      select jsonb_agg(v) from jsonb_array_elements(coalesce(s->'videos','[]')) v
      where v->>'id' <> vid
    ), '[]'::jsonb),
    'sentences', coalesce(s->'sentences','{}'::jsonb) - vid,
    'jobs', coalesce((
      select jsonb_agg(j) from jsonb_array_elements(coalesce(s->'jobs','[]')) j
      where j->>'videoId' <> vid
    ), '[]'::jsonb)
  );
$$;
~~~

事务伪代码（边界都必须在服务端完成）：

~~~sql
BEGIN;
-- SECURITY DEFINER + set search_path = ''；
-- public.is_admin() 必须为 true；客户端不允许访问 private 表。
SELECT * FROM private.content_snapshots
 WHERE environment = 'production' FOR UPDATE;
-- ASSERT revision = expectedRevision
-- ASSERT 全部目标的后台任务均为终态
-- INSERT private.content_video_trash：
-- 保存每个 ID 在 draft / published 各自对应的视频、字幕和任务原件
-- INSERT private.content_tombstones：删除时间、被屏蔽的 jobId、mediaGeneration
-- 对每个 ID 分别计算：
-- draft = private.without_video(draft, id)
-- published = private.without_video(published, id)
-- UPDATE revision = revision + 1, updated_by = auth.uid(), updated_at = now()
-- INSERT 审计事件与 requestId 执行结果
COMMIT;
~~~

重点：从 draft 和 published **分别删除目标**，而不是把整个 draft 重新投影为 published，否则可能同时发布其他尚未完成审核的编辑。

恢复事务只将原件放回 draft，状态强制 DRAFT；保持 published 不变。
线上回收站、审计、删除标记不放进学生 get_published_content 响应。

### 7.3 永久删除媒体：事务 outbox，而非前端直接调用 R2

~~~ts
type PurgeTask = {
  id: string;
  videoId: string;
  generation: number;
  status: 'PENDING' | 'RUNNING' | 'RETRY' | 'DONE';
  objectKeys: string[];   // 服务端根据媒体索引生成，拒绝客户端任意路径
  attempts: number;
  nextAttemptAt: string;
};
~~~

永久删除按钮要再次确认，并明确“原视频、封面、480/720/1080 分片、字幕文件不可恢复”。服务器应：

1. 锁定内容；确认仍在回收站、达到保留期、无处理任务和其他视频引用。
2. 把该媒体 generation 标为 PURGING，使恢复/发布拒绝引用该版本。
3. **同一数据库事务**写 outbox，提交后由 Worker 消费。
4. Worker 分批删除，记录进度，失败重试；已不存在的对象按成功处理。
5. 全部成功后标记 DONE，再清理不再需要的元数据。
6. 不把任务文件和源文件路径交给浏览器自由填写，不使用递归删除桶根目录。

R2 消费器中的实际 API 调用形式：

~~~js
// 只演示删除对象这一段；lease / generation / 引用检查由服务端仓储层完成。
async function deleteR2Objects(bucket, keys) {
  if (!Array.isArray(keys) ||
      keys.some(key => typeof key !== 'string' ||
        !key.startsWith('videos/') || key.includes('..'))) {
    throw new Error('INVALID_MEDIA_KEYS');
  }
  for (let start = 0; start < keys.length; start += 1000) {
    await bucket.delete(keys.slice(start, start + 1000));
  }
}
~~~

上面的前缀检查不能替代数据库媒体归属检查。必须用服务端枚举出来的完整对象清单（master.m3u8、各清晰度子清单/分片、原片和封面），不能只删 MP4 留下一堆 HLS 分片。

当前线上 functions/api/media.js 主要校验“已登录 + key 格式”，**还没有逐视频发布状态/删除状态授权**。上线云删除之前必须补上：
- 登录用户可看的 published 视频与 mediaKey 关联查询；
- 已删除/下架返回 404 或 410；
- 取消或缩短撤销权限场景下的私有缓存；
- 受保护 HLS 的 manifest 与分片都走一致授权，不只保护 master 文件。

本地媒体永久删除也应由 Python Worker 按 jobId 解析路径：
resolve 后必须位于 local-data/studio/sources 或 media 对应 job 的子目录，确认任务终态且无其他引用再删除。浏览器不传 Windows 路径。本轮没有启用该物理删除功能。
